# OpenGlyph benchmark results

OpenGlyph **1.1.0-preview** (MIT fork of UniText 1.0) vs **TextMeshPro** and **UI Toolkit**.
Methodology follows UniText's published marketing methodology — **100 objects, 10
iterations, 3 warmups, ~2300 characters per object** (Latin + Arabic + Hebrew +
Mixed), `UniText.UseParallel = false` — and **adds** a parallel-ON OpenGlyph pass.

> Generated by `Benchmarks~/Assets/Benchmarks/BenchmarkRunner.cs`. Raw JSON is
> committed under `Benchmarks~/Results/`. Reproduce with
> `pwsh Benchmarks~/Tools~/run-benchmarks.ps1 -Do windows` (and `-Do smoke`).

### Important honesty notes (read before the numbers)

1. **IL2CPP was requested but is not installed on this build host.** Unity
   6000.3.19f1 here ships only the **Mono** variations of Windows Build Support
   (no "Windows Build Support (IL2CPP)" module), so the representative Windows
   player is **Mono/Release, not IL2CPP**. The build script
   (`BenchBuild.BuildWindows`) auto-detects this and falls back to Mono, logging
   how to install IL2CPP. IL2CPP would typically make OpenGlyph's managed
   shaping/layout faster; **treat these as a Mono lower bound.**
2. **TMP cannot shape Arabic/Hebrew without a third-party plugin.** For TMP the
   Arabic / Hebrew / Mixed rows measure **unshaped fallback glyph runs, NOT
   equivalent rendered output** — they are *not* apples-to-apples. The fair TMP
   comparison is **Latin only**; non-Latin TMP rows are marked `fair=false`.
3. **TMP numbers come from the editor smoke run, OpenGlyph & UI Toolkit from the
   Windows player.** In the built player, every `TextMeshProUGUI.Awake` threw
   `TMP_Settings.get_autoSizeTextContainer` NRE (TMP's settings asset did not
   resolve at runtime in this project), so player-side TMP timings are
   unreliable. TMP's essentials loaded correctly in the editor, so TMP is
   reported from the **editor smoke** (labelled). This is a project-config gap,
   not a TMP-vs-OpenGlyph performance fact — see "Reproduce / fix" below.
4. **OpenGlyph is much slower than TMP/UI Toolkit on the per-object phases, and
   this report says so plainly** (next section). OpenGlyph does full HarfBuzz
   shaping + FreeType SDF rasterisation per build; TMP uses a pre-baked atlas and
   no complex shaping; UI Toolkit's `Label` is extremely light. OpenGlyph buys
   correctness (real BiDi/shaping) at a real CPU cost.
5. **Allocation metric** is `Profiler.GetMonoUsedSizeLong()` deltas (used managed
   heap), clamped to ≥0 — coarse (a GC between samples hides allocations), so
   small MB/KB values near 0 mean "below the noise floor", not "zero garbage".
   GC collection counts were 0 across the measured window for all systems.

## Speedup vs TMP (Latin, the only fair cross-system row)

Using the fair Latin Object-Creation medians (OpenGlyph from the Windows player,
TMP from the editor smoke — different runtimes, so this is **indicative**, not a
clean ratio):

| System | Latin creation (ms) | vs TMP |
|---|---|---|
| TMP (editor) | 5.66 | 1.0× (baseline) |
| OpenGlyph parallel ON (player) | 51.7 | **~9× slower** |
| OpenGlyph parallel OFF (player) | 117.1 | **~21× slower** |
| UI Toolkit (player) | 0.5 | ~11× faster |

**Plainly: OpenGlyph is the slowest of the three on raw per-object throughput.**
Parallel mode roughly **halves** OpenGlyph's creation/rebuild cost (117→52 ms
Latin; 169→55 ms Arabic). OpenGlyph's value is correctness (real UAX#9 BiDi,
HarfBuzz shaping, Arabic/Hebrew that TMP cannot do unaided), not speed.

## Parallel OFF → ON (OpenGlyph, Windows player)

| Text set | Creation OFF→ON | Full Rebuild OFF→ON | Speedup (creation) |
|---|---|---|---|
| Latin  | 117.1 → 51.7 | 106.1 → 46.1 | **2.26×** |
| Arabic | 169.2 → 54.6 | 161.3 → 49.9 | **3.10×** |
| Hebrew | 121.7 → 40.1 | 112.5 → 34.6 | **3.03×** |
| Mixed  | 123.7 → 44.4 | 115.7 → 38.7 | **2.78×** |

Parallel scaling is strongest on the heavier scripts — expected, since there is
more per-object shaping work to spread across the 12 cores.

## Glyph rasterisation (adding N glyphs to the atlas)

| Engine | Glyphs | Total ms | ms / glyph | Notes |
|---|---|---|---|---|
| **OpenGlyph FreeType** (SDF pack) | 200 | 58.95 | **0.295** | `UniTextFont.TryAddGlyphsBatch` — FreeType raster + SDF bake into atlas (Windows player) |
| Unity FontEngine (TMP dynamic) | — | — | — | **not measured**: `TMP_FontAsset.CreateFontAsset` / `TryAddCharacters` threw a `TMP_Settings` NRE in this project (same settings gap as note 3). Needs TMP essentials fully wired. |

So we have a real OpenGlyph FreeType rasterisation number (**~0.30 ms/glyph** at
48 px, SDF) but **not** a Unity FontEngine comparison — reported honestly rather
than fabricated.

OpenGlyph trades a larger shipped font payload (uncompressed TTF, no subsetting
in this preview) for runtime shaping flexibility. A future font-compression /
subsetting pass is the obvious win here.

## What ran where

| Run | Status | Backend | Representative? |
|---|---|---|---|
| (a) Editor play-mode (batchmode) | ✅ all 16 combos + OpenGlyph glyph raster | Mono (editor JIT) | **No** — editor overhead |
| (b) Windows x64 standalone player | ✅ built + ran, all 16 combos + raster | **Mono/Release** (IL2CPP module absent) | **Yes** |
| (c) Android IL2CPP Release APK | ✅ **built** `OpenGlyphBench.apk` (27.38 MB, IL2CPP/Release, ARM64) — cannot run here (no device); install+run with `run-android.ps1` | **IL2CPP/Release** | runs on your device |

> The Android APK built with **IL2CPP** (bundled SDK/NDK/JDK present on this host),
> unlike Windows (IL2CPP module absent → Mono). Output was placed on D: at
> `D:\OpenGlyphWork\scratch\benchmarks\build\Android\OpenGlyphBench.apk` to spare
> the near-full C: drive; `run-android.ps1` defaults to that path. On a connected
> Quest/Android device it installs, launches, waits, and pulls
> `android_il2cpp_results.json` into `Results/`.

## Reproduce / fix

- **Representative Windows run:** `pwsh Benchmarks~/Tools~/run-benchmarks.ps1 -Do windows`
- **Editor smoke:** `pwsh Benchmarks~/Tools~/run-benchmarks.ps1 -Do smoke`
- **For an IL2CPP Windows run:** install *Windows Build Support (IL2CPP)* via Unity
  Hub for 6000.3.19f1, then re-run — `BenchBuild.BuildWindows` auto-selects IL2CPP.
- **To get valid TMP player numbers + the FontEngine raster comparison:** ensure
  TMP essentials resolve at runtime (the import is committed under
  `Assets/TextMesh Pro/`, but `TMP_Settings` must be referenced from a `Resources`
  folder and the project TMP settings pointer set). The editor smoke has valid
  TMP timings; the FontEngine glyph-raster still needs the settings fix.
- **Android:** build with `-Do android`, then on a connected device run
  `pwsh Benchmarks~/Tools~/run-android.ps1` (installs, runs, pulls the JSON).
